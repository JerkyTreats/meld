# Architecture Response

Explain the concrete behavior that is wrong or impossible before naming the abstraction intended to correct it. When current code causes the failure, name the implemented path and keep evidence close to the claim.

State one sharp architectural thesis in ordinary language. Separate owners, products, and transitions without hiding behind layer terminology.

Preserve distinctions between desired state and causal work, semantic construction and execution, durable transport and domain grammar, runtime participation and implementation write scope.

Use current repository terms when they remain accurate. Explain a rejected or superseded term once, then use the preferred term consistently.

Distinguish implemented facts, supported inference, proposals, and unresolved edges. Link primary evidence instead of reproducing every assessment table.

Write as a thoughtful collaborator. Prefer cohesive prose and use headings or structured visuals only when they materially clarify the relationships.

When delegated review contributes, synthesize its judgment. State what each review established, what it corrected, and where its evidence remained limited.

End at the authorized scope. State what was produced, what remains unresolved, and what remains unauthorized. Do not silently turn assessment into requirements, planning, or implementation.
