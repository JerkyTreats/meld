# Bidirectional Review Synthesis: PDS Declaration And Compiler Boundary

Date: 2026-08-08
Status: architecture synthesis
Inputs:
- [Top-Down Review](top_down_intent_review.md)
- [Bottom-Up Review](bottom_up_runtime_review.md)

## Question

Do the current docs-freshness, CVE, and expanded PDS examples represent the eventual user-facing PDS expression, or are they better understood as material below that layer?

## Independent Agreement

The two reviews start from opposite constraints and reach the same conclusion.

### Top-down

The principal needs to express:

```text
what should be stewarded
where
under what policy
with what autonomy
within what budget
when to escalate
what verification is required
```

The principal should not need to author evidence schemas, comparator factors, method realizations, task-network mechanics, or runtime actor topology.

### Bottom-up

The runtime requires:

```text
belief semantics
evidence routes
curation semantics
maintained conditions
methods
afforded actions
method realizations
task-package semantics
outcome verification
authority/governance requirements
```

Those forms must be resolved deterministically and versioned without adding expression-specific root runtime branches.

The resulting architectural gap is the compiler/linker boundary between those two views.

## Refined Representation Stack

The reviews support this model:

```text
USER / PRODUCT AUTHORING SURFACE
    conversational UI / form / concise config / SDK
    ↓ canonicalize

CANONICAL PRINCIPAL DECLARATION
    durable, diffable, approvable intent and policy
    ↓ combine with

EXPERT PACKAGE / DOMAIN FACET SOURCE
    domain vocabulary, semantic presets, belief and evidence theory,
    actions, verification profiles, governance requirements
    ↓ compile / link

COMPILED STEWARDSHIP IMAGE
    normalized, content-addressed linked semantic IR
    ↓ install / lower

DOMAIN-OWNED OPERATIONAL THEORY CONTRACTS
    belief registry, mappings, curation, meld-lang/planning,
    actions, packages, outcome contracts, governance bindings
    ↓ execute

DOMAIN-OWNED RUNTIME STATE
    events, graph, evidence, beliefs, decisions, goals,
    plans, tasks, approvals, outcomes, projections
```

This model gives each authoring population a separate contract:

- principal/customer authors the declaration;
- domain/package experts author package/facet semantics;
- compiler/linker produces the image;
- runtime domains own execution and live state.

## Why "The Current Examples Are IR" Is Directionally Correct But Incomplete

The current examples were developed from the runtime upward. They therefore contain material that belongs below the principal declaration.

However, two categories are mixed together.

### Expert-authored semantic source

Examples:

```text
what `strict` means for CVE exposure
which evidence sources are admissible
what constitutes a canon correction
which actions a steward family supports
what `release_grade` verification means
which claim classes a lore definition requires
```

These semantics should not necessarily be generated by a compiler. Domain experts may author them as package/facet source.

### Compiler/linker output

Examples:

```text
resolved package/facet revisions
resolved belief-family revision ids
resolved evidence mapping revisions
lowered maintained propositions
meld-lang methods/operators/effects
available-action bindings
method realization bindings
task-package references
linked outcome contracts
resolved governance requirements
content hashes and lineage
```

These are semantic IR / compiled-image material.

Therefore the current examples are best described as:

> **compiler-target and package-source design fixtures**, not end-user declarations.

## Architectural Boundary 1 — Principal Approval

The principal approves the canonical declaration, not the compiled image.

The declaration should answer:

```text
What responsibility did I create?
What is in scope?
What outcomes should be maintained?
What may the steward do?
What may it not do?
When does it escalate?
What evidence is required before restoration is accepted?
```

A semantic diff at this level is the product approval surface.

## Architectural Boundary 2 — Package Semantic Authority

The package/facet revision defines the meaning of named selections.

For example:

```text
sensitivity: strict
verification: source_backed
autonomy: draft
```

have no universal PDS meaning. The selected package/profile revision expands them into domain-specific theory.

This prevents the root PDS layer from accumulating a universal ontology or universal risk language.

## Architectural Boundary 3 — Compiler Truthfulness

The compiler may:

- resolve symbols;
- expand declared presets;
- link package/facet revisions;
- normalize identities;
- validate cross-domain contracts;
- lower into domain-owned IR;
- compute content identities;
- produce activation requirements.

The compiler may not:

- invent missing domain semantics;
- expand authority beyond the declaration/grant;
- fabricate runtime capabilities;
- hide an unsupported semantic seam in prompt text;
- select arbitrary undocumented defaults.

Missing meaning remains unresolved.

## Architectural Boundary 4 — Runtime Independence

New PDS applications should enter through data and linked theory, not expression-name branches.

The extension test is:

```text
new steward family
    -> new/updated expert package or facets
    -> new principal declaration/profile selection
    -> compiler/linker output
    -> existing domain seams
```

If a roleplay, lore, CVE, learner, or reliability steward requires:

```text
match expression_name {
    ...application semantics...
}
```

inside root runtime code, the abstraction has failed or a missing domain contract has been discovered.

## Architectural Boundary 5 — Dual Identity And Lineage

At least two durable identities answer different audit questions.

### Declaration revision

Answers:

```text
What did the principal authorize?
```

### Compiled image revision

Answers:

```text
What exact linked semantics did the runtime execute?
```

Runtime records then cite the exact installed domain-theory revisions that produced their state.

The lineage is therefore conceptually:

```text
principal declaration revision
    + package/profile/facet revisions
    + assignment/activation revisions
        ↓
compiled image revision
        ↓
installed domain-theory revisions
        ↓
runtime evidence / belief / decision / plan / outcome lineage
```

## Architectural Boundary 6 — Two Semantic Diffs

The system should eventually support two different diffs.

### Declaration diff

Principal-readable:

```text
scope expanded
autonomy increased
verification strengthened
exception approval changed
budget reduced
```

### Compiled-image diff

Expert/operator-readable:

```text
belief-family revision changed
mapping rules changed
method set changed
action realization changed
outcome contract changed
```

A compiled diff can reveal meaningful package upgrades even when the principal declaration text remains unchanged.

## Consequences For The Example Corpus

The examples should continue to be detailed. Their value is to pressure-test the compiler target and package semantics.

They should not be simplified into user syntax merely to look product-facing.

Instead, each example should maintain explicit views of:

1. principal intent;
2. canonical declaration selections;
3. expert package/facet semantics;
4. compiled semantic IR requirements;
5. runtime state and verification behavior.

The existing [Compilation Layer Span](../examples/compilation_layer_span.md) is the beginning of this structure.

## Decisions Supported By Both Reviews

1. Do not freeze current theory JSON/YAML as the user-facing PDS language.
2. Preserve a durable canonical declaration above compiled theory.
3. Treat current docs/CVE theory bundles as compatibility antecedents of compiled output.
4. Distinguish expert-authored package/facet source from generated IR.
5. Prefer a linker over domain-owned semantic fragments to a monolithic PDS runtime AST.
6. Require deterministic, content-addressed compilation and revision lineage.
7. Do not expose runtime substrate merely because it is strongly typed.
8. Do not allow new steward families to extend via root application branches.
9. Add runtime seams before allowing upper layers to depend on semantics the runtime cannot yet represent.
10. Preserve traceability from every compiled choice to either principal authorization or expert package semantics.

## Remaining Design Questions

The reviews do not settle:

- the exact canonical declaration schema;
- whether package/facet source is central or federated;
- how principal declaration and assignment are divided;
- whether activation is embedded or separately versioned;
- how package defaults are materialized in declaration diffs;
- exact image manifest structure;
- which currently injected theory kinds receive durable registries first;
- how compiled-image upgrades require reapproval when the principal declaration is unchanged.

These are now better-scoped questions because the architectural layers are separated.

## Final Assessment

The bidirectional interrogation validates the compiler interpretation.

The strongest formulation is:

> The current PDS examples are **runtime-up design fixtures spanning expert package source and hand-lowered semantic IR**. They define what a PDS compiler/linker must eventually be able to express. The principal-facing PDS declaration is a separate, higher-level, durable approval representation whose symbols lower through selected package/facet revisions into that compiled image.
