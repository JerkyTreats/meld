# Codebase Quality Router Specification

Date: 2026-08-18
Status: discovery router exercise aligned to canonical PDS boundary
Scope: fan codebase quality through `theory::router` and record pressure on the common theory set

## Purpose

This exercise tests whether one package can install a federation of concern-specific stewardship semantics without asking `theory::router` to interpret software quality, construct Agents, or arbitrate objectives.

It also pressures shared observation, overlapping effects, multiple runtime placements, and aggregate activation across several charters.

## Semantic Package And Runtime Input Map

The exact semantic component count is profile dependent. This map also lists runtime inputs that activation and Strategy resolve independently.

| Component group | Candidate route | Installing owner | Owner meaning |
| --- | --- | --- | --- |
| `quality-policy` | `software-quality.policy.v1` | software-quality domain candidate | selected concern profiles, protected floors, verification posture |
| each concern belief | `world-model.belief-family.v1` | belief domain | one concern-specific epistemic question |
| `quality-action-cost` | `world-model.belief-family.v1` | belief domain | expected bounded action cost |
| `quality-action-value` | `world-model.belief-family.v1` | belief domain | observed downstream action value |

| each concern condition | `world-model.agent-maintained-condition.v1` | Agent domain | explicit floor and restoration region |
| each concern strategy | `world-model.strategy-theory.v1` | Strategy domain | settlement, prospective evidence, abstract action, outcome, and constraint meaning |

`software-quality.policy.v1` is a candidate owner route. It is not part of the settled router contract. The exercise needs an owner for concern selection and protected-floor meaning, but it does not settle whether that owner is one software-quality domain or a composition of existing domains.

## Router-Owned Semantics

The router owns package structure, route dispatch, exact owner references, structural closure, receipts, and historical exact resolution.

It does not know which concern is more important, how test health differs from performance health, whether one benchmark is comparable, how several charters map to runtime Agents, whether two actions conflict semantically, or whether a patch restored any condition.

The package may be large, but component count does not widen router meaning.

## Owner Semantics And Cross Links

Belief owners install distinct concern families. Agent owners install one or more curation and maintained-condition components. The Strategy route owns concern-specific settlement and action meaning. Strategy separately owns Methods and problem construction. Capability and execution own exact contracts, claims, authority, and effect identities.

The candidate software-quality policy owner validates selected profiles, concern-specific floors, protected-floor relationships, and verification posture. It must not duplicate canonical test, docs, benchmark, or repository products.

Expected exact links include:

```text
outcome mapping
→ exact producer product schema and concern belief family

maintained condition
→ exact concern family and restore threshold

strategy theory
→ exact maintained condition and capability contracts

quality policy
→ exact selected concern components and protected floors

activation contribution
→ owner-scoped package view and assignment bindings
```

Structural requirements prove component presence. Owner semantic linking proves that a test product is not used as a migration-safety verdict or a patch receipt as a restored outcome.

## Assignment And Charter Cardinality

One package receipt may support many assignments. One assignment may select several concern profiles. The unresolved question is whether each selected charter becomes a separate Agent activation, one Agent with several maintained conditions, or an owner-defined combination.

The router must not choose that cardinality. Its responsibility ends with exact component closure and owner-scoped references.

Whichever activation shape is chosen must preserve independent concern evidence and perspective, exact principal and scope, protected-floor relationships, assignment-local capability selection, attributable decisions and outcomes, and lifecycle closure for every required owner contribution.

## Activation

Potential owner-scoped bindings include:

```text
workspace and repository
subject selection
test and benchmark profiles
toolchain executables
isolated branch target
CI callback identity
provider only for selected model-backed behavior
```

Preparation resolves exact components, selected charters, observation subscriptions, capability selectors, binding refs, authority posture, admission policies, and inert invoker drafts.

Start creates generation-scoped tool, provider, callback, and Agent handles. Readiness proves every required concern path without exposing new work before the aggregate current-generation fence advances.

Optional concern degradation is valid only when both package semantics and activation policy declare it. A missing required persistence verifier cannot be hidden by a ready performance adapter.

## Capability And Authority Closure

Capabilities remain atomic and exact. A model-backed coding adapter may physically inspect, edit, test, commit, and open a pull request, but the assignment-local catalog exposes only selected contracts and effective authority.

Cross-concern reuse does not create authority. One accepted test observation can support several belief mappings, but a reliability grant does not authorize a performance patch.

Effect identities include exact repository, worktree or branch, path scope, and mutation class. Overlapping effects are arbitrated by execution even when two concern strategies independently select them.

## Observation And Result Admission

Each producer domain validates its own result before canonical append. Relevant lineage includes:

- assignment and package receipt
- activation, activation generation, and participant incarnation
- exact capability and policy revisions
- durable operation key and attempt id
- repository and workspace revision
- test environment or benchmark workload identity
- adapter implementation and artifact identity
- declared coverage and completeness

A test pass, benchmark report, generated patch, opened review, and later outcome remain distinct products.

The world-model outcome mapping cites exact admitted product classes. It does not parse raw tool output or infer success from transport status.

## Shared Observation Pressure

Several charters may request the same test, repository snapshot, or source inspection. Compatible work may be deduplicated only when subject and source revision are exact, requested observation semantics match, authority and binding contexts permit reuse, completeness satisfies every consumer, and the admitted product preserves producer provenance.

Deduplication may share one product or execution attempt. It must not merge beliefs, goals, curation, or outcome judgments.

This pressure suggests shared observation identity below the steward layer, not a generic router-owned quality cache.

## Conflict And Effect Pressure

Two charters may select actions with overlapping effects or opposing predictions. The router cannot arbitrate because it has neither live goals nor domain meaning.

Execution can prevent unsafe simultaneous dispatch through exact effect claims. Strategy and Agent semantics can expose predicted improvements and protected-floor risks. A higher-level coordination bridge may request a combined method or principal decision.

The unresolved bridge is normative. Effect exclusion alone prevents collision but does not choose which quality objective should win.

## Isolation Pressure

One assignment may use an in-process parser, local test subprocess, shared repository index, remote model, and external CI callback simultaneously.

Isolation remains per axis and owner. Exact concern revisions prevent semantic bleed. Charters retain independent current beliefs and goals. Tools receive only required workspace and credential bindings. Benchmarks and tests retain resource budgets. Repository mutations use exact effect scopes. Remote and CI results pass owner admission. Historical work retains its package and generation lineage.

Sharing one workspace or index never implies shared provider context, grants, Agent perspective, or current state.

## Lifecycle Pressure

Aggregate activation becomes harder as selected charters and adapters multiply. Prepared closure must include every required owner receipt while remaining inert. Runtime publication waits for all required readiness evidence.

Quiescence closes new claims, settles or suspends accepted tests and mutations, persists draft artifacts and outboxes, checkpoints CI subscriptions, drains admitted events, and records concern safe points. Shutdown order follows operational dependencies rather than package declaration order.

A long benchmark or CI run may finish after replacement. Its old generation and exact source revision remain visible. The result may be historical evidence, but it cannot silently settle a current condition over newer source.

## Interaction With Other Stewards

Canonical event cooperation keeps ownership explicit:

```text
security violation or docs assessment
→ optional evidence for selected quality concerns

quality-authorized code change
→ repository fact

repository fact
→ independent docs, security, test, and quality observation opportunities

service incident outcome
→ reliability and action-value evidence where explicitly mapped
```

No package component commands another assignment. Shared facts do not share authority.

## Router Falsification Findings

Reject or narrow the model if:

- the router must understand concern priority to install the package
- route declaration order determines charter priority or activation order
- package closure cannot represent several exact belief and Strategy components
- sharing an observation requires sharing Agent state
- one generic tool success product must satisfy all quality outcomes
- execution effect arbitration requires importing software-quality bodies
- historical benchmark or test evidence resolves through current package heads
- one missing concern adapter can be hidden behind aggregate ready status

The example reveals that structural package closure and runtime readiness closure are separate aggregates. Both need exact per-owner membership, but neither should interpret concern meaning.

## Theory-Set Implications

### Common Candidate Mechanism

The example supports repeated routed components of the same route, explicit exact dependencies among them, owner-scoped package views, assignment-local capability catalogs, atomic capability contracts, exact effect claims, shared admitted observations, and aggregate activation readiness.

It also supports keeping package order, semantic priority, lifecycle order, and event order as four distinct concepts.

### Owner-Specific Meaning

Concern selection, quality floors, benchmark comparability, migration safety, usability confidence, maintainability, and cross-concern consequence meaning remain with software and producer domains.

The router should see exact bodies and references but no universal quality schema.

### Unresolved Bridge

Open bridges include:

- the owner and shape of software-quality profile composition
- assignment-to-charter and Agent activation cardinality
- reusable observation identity and admission across several consumers
- normative conflict mediation above effect exclusion
- aggregate readiness and safe-point ownership for a multi-charter assignment
- how action cost and value transfer across comparable regimes without false sharing

These remain discovery questions.

## Non Commitments

This exercise does not approve `software-quality.policy.v1`, a charter cardinality, a conflict system, tool providers, runtime topology, or a migration plan.
