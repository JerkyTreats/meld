# Persistent Domain Stewardship

Date: 2026-08-19
Status: active canonical architecture
Scope: the semantic boundary from principal declaration through operational domain theory into the Meld cognitive runtime

## Thesis

Persistent Domain Stewardship is the program by which durable domain meaning reaches Meld as declarations rather than application branches in runtime code.

PDS is a semantic program for cognition. It is not a cognitive program.

PDS declares the stable meanings, questions, norms, and proof obligations under which a domain may be stewarded. Meld grounds those declarations against a current subject, perspective, world state, capability catalog, and authority context. Meld alone produces situated evidence, beliefs, Goals, Strategy candidates, authorizations, tasks, outcomes, and reassessments.

## Canonical Layer Stack

```text
principal intent surface
    ↓ canonicalize
principal declaration
    ↓ select and bind
PDS semantic package
    ↓ install through owner routes
operational domain theory revisions
    ↓ ground and combine with current runtime inputs
Meld cognition and execution
```

The principal declaration records responsibility, scope, policy selections, requested autonomy, authority posture, budget, escalation, and verification. The PDS package supplies stable domain semantics. Assignment supplies principal, subject, perspective, branch, and grant lineage. Activation supplies physical bindings, exact capability offers, provider and credential bindings, isolation, quotas, and lifecycle identity.

These layers have separate identities because they answer separate audit questions.

## PDS Semantic Authority

PDS may supply stable domain meaning in these forms:

- domain vocabulary, identity classes, and proposition meaning
- relevant event and fact kinds
- belief questions and admissible evidence classes
- support, contradiction, coverage, currency, and proof semantics
- maintained conditions and normative domain policy
- settlement obligations and prospective evidence requirements
- semantic constraints and outcome interpretation
- governance classifications and activation requirements

PDS may reference owner-defined policies by exact revision. The owning domain remains authoritative for their schemas and validation.

PDS does not supply:

- current observations, facts, findings, or source state
- admitted evidence or belief revisions
- current confidence or target-shaped conclusion values
- Goal instances or Agent decisions
- an exact active capability catalog
- capability action classes or capability-to-theory mappings
- a selected Method or action topology
- Strategy evaluation policy or search bounds
- a static projection request for every future Goal
- effective authority, authorizations, tasks, operations, or outcomes

State-free theory is necessary but insufficient. A state-free body still violates this boundary when it fixes an active toolbox, an action chain, a target conclusion, or a situated inference result.

## Domain Ownership

| Meaning or artifact | Authority |
| --- | --- |
| package envelope, imports, routes, exact receipt | PDS theory router |
| domain component schema and semantic validation | routed owner domain |
| current facts and graph projection | source and world-model graph owners |
| evidence admission, inference, and belief revision | belief |
| maintained-condition evaluation and Goal creation | Agent |
| planner projection | world-model planner |
| Strategy problem construction, search, verification, and candidates | Strategy |
| exact current capability contracts, implementations, and active catalog | capability and activation |
| construction policy and candidate judgment | Agent |
| effective authority and dispatch enforcement | Agent plus execution |
| tasks, operations, effects, and realization | execution |
| substantive domain outcome admission | result owner plus events |
| outcome evidence and reassessment | belief plus Agent |

Root configuration and runtime assembly are adapters. They resolve exact identities and supply explicit inputs to owner contracts. They do not interpret application meaning.

## Strategy Input Boundary

The canonical Strategy input is assembled from independently owned parts.

```text
ground Goal
+ exact planner snapshot
+ complete active runtime capability snapshot
+ separately admitted Method snapshot
+ Agent-selected construction policy
+ explicit authority context
→ immutable StrategyProblem

StrategyProblem
+ engine identity
+ search bounds
+ optional deterministic seed
→ StrategySearchRequest
```

### Capability snapshot

Capability providers publish exact executable contracts independently of PDS. Activation binds the complete catalog available to one assignment generation. Strategy receives one immutable snapshot of that catalog. Search may reject irrelevant capabilities, but no PDS package supplies a shortlist or a parallel action vocabulary.

Capabilities are universal, PDS-theory-free runtime primitives. PDS-theory-free means that a Capability does not carry PDS settlement, belief, or maintained-condition meaning. Its own contract still truthfully declares typed inputs, outputs, bindings, scope, operational effects, and execution behavior.

A PDS distribution may co-ship a normal capability contributor or an external implementation binding. Co-shipping does not make that Capability part of the PDS semantic body. Availability still enters through the ordinary runtime contribution and activation path.

### Method snapshot

Methods are separately admitted Strategy knowledge. They may be expert-authored, learned, or retained as compatibility forms, but they are candidate generators rather than PDS mandates. A PDS package may define the semantic vocabulary against which a Method is validated. It does not install an action topology as stewardship meaning.

### Construction policy and search controls

The Agent selects the construction policy that defines eligibility, comparison, risk, cost, uncertainty, and alternative retention for the current Goal class. Strategy applies it. Search bounds and engine controls belong to the request and never become domain truth.

### Projection and authority

Projection needs are derived from the Goal, current epistemic structure, Method requirements, and candidate capability preconditions. They are not a static package list.

PDS may define governance meaning. Assignment records the principal request and grant lineage. A candidate derives its exact authority requirements from selected actions. Agent judgment and execution independently establish and enforce effective authority.

## Evidence Boundary

Evidence that bears directly on a maintained proposition must preserve sufficient lower ground for owner admission, explanation, replay, and falsification. Applicable ground includes subject, source facts, source revisions, policy revision, evidence class, coverage, contradictions, currency, calculation identity, completeness, and producer lineage.

A domain assessment may be admitted as evidence. Its conclusion does not become a belief merely because the producer calls the subject fresh, clean, safe, correct, or restored. A target-shaped scalar without independently admissible lower grounds is insufficient by itself.

Operational success never substitutes for semantic proof.

```text
task completion
!= domain outcome
!= admitted evidence
!= belief revision
!= maintained-condition restoration
```

## Capability Atomicity

A capability may hide deterministic implementation mechanics that do not change Strategy-relevant meaning. Internal choices must become visible when they materially change alternatives, authority, cost, risk, cardinality, expected outcomes, or verification.

Visibility may take either form:

- expose separate composable capability contracts
- retain one atomic contract while publishing truthful bounds and observed economics

An atomic contract must not conceal a procedural mini-strategy whose branching would have changed candidate selection.

## Counterfactual Conformance

The boundary is healthy only when these variations remain possible:

```text
same theory plus different evidence
    may produce different beliefs

same belief plus different maintained intent
    may produce different Goals

same Goal plus different capability snapshot
    may produce different Strategy candidates

same candidate plus different authority context
    may produce different admission decisions

same execution result plus different admitted proof
    may produce different restoration judgments
```

If an earlier declaration already fixes the later artifact, cognition has crossed the interface in the wrong direction.

## Package And Router Boundary

The PDS router owns structural composition only:

- bounded package materialization
- exact imports and content identity
- route lookup and compatibility
- package-local cardinality and structural requirements
- owner validation and installation dispatch
- exact owner revision receipts
- historical exact resolution

The router does not decode domain bodies, select capabilities, assemble Strategy problems, interpret evidence, grant authority, activate providers, or construct runtime artifacts.

Capability contribution is a separate publication path. A PDS package may declare physical activation requirements such as a required provider class or executable binding. It may not declare a Capability catalog, Capability shortlist, parallel operator catalog, or Capability-to-theory mapping. Exact active contracts and implementation offers are activation products rather than semantic package components.

## Native Meld Resolution

PDS meaning enters Meld through its owning semantic domains. Those owners lower declarations and current evidence into graph-addressed epistemic products, belief views, maintained-condition divergence, and Goals.

Strategy consumes those native products together with the complete active Capability catalog. Agent authorization preserves the exact candidate Composition. Execution lowers that Composition into Tasks and the Task Network. PDS does not introduce another planning, Capability, evidence, or graph substrate between these owners.
