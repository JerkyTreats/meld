# Integrated Product Proof And Inspection Detailed Design

Date: 2026-08-22

Slice: `WMR-DD-07`

Status: Startup integration candidate for `WMR-DG-07` revision 3

Implementation authorization: none

## Decision

The integrated proof is a resolution graph over already accepted owner and lifecycle positions. Inspection may correlate and present those identities, but it cannot create semantic truth, repair missing evidence, advance a cursor, classify an outcome, judge a Goal, or change lifecycle state.

`WMR-H18` is therefore a proof projection only. Every producer-consumer relationship it displays is already owned and closed by `WMR-DG-01` through `WMR-DG-06`.

## Complete Docs Freshness Proof

### Already-Correct README

1. The current generation cites the exact docs product compilation, assignment, owner revisions, Agent topology, participant realizations, and readiness receipts.
2. Workspace and docs publish exact observation batches and completeness receipts.
3. Events accepts neutral publications. Graph and configured Belief advance independently as required by installed routes.
4. Agent consumes one complete PlannerCut and judges the installed maintained condition against current evidence.
5. If the desired condition is already satisfied, Agent records reconciliation without authorizing a Task.
6. Owners publish exact checkpoints and waits with viable wakes. Lifecycle may project quiescent only when every realized participant closes those positions.

Expected result: no Task exists because no executable work is justified. Absence of a Task is supported by a positive Agent decision and complete current evidence, not by inactivity.

### Missing Or Incorrect README

```text
complete docs observation
-> Events and Graph visibility
-> configured Belief revision
-> PlannerCut
-> Agent Goal decision
-> Strategy Plan with exact product dependencies
-> independent Agent Epistemic Operation authorization
-> Curation acceptance, terminal result, and declared visibility
-> Agent prerequisite milestone absorption
-> independent Agent Task authorization
-> Execution admission, attempt, operation, and outcome
-> workspace and docs re-observation
-> returned Event, Graph, and optional configured Belief positions
-> exact Agent milestone absorption
-> separate Goal disposition
```

Every arrow resolves an accepted handoff edge. A rejected Curation operation leads to hold, Plan conflict, or successor handling and never makes the dependent Task eligible. An accepted operation must reach its terminal Curation result, required Event and Graph or configured Belief visibility, and exact Agent milestone absorption before dependent Task authorization. Plan construction does not grant product authority. Execution outcome does not prove owner truth. Returned owner evidence does not prove Agent acceptance. Agent product progression does not prove Goal satisfaction.

### Partial, Failed, Or Uncertain Work

Execution retains exact attempt, binding, target, operation, and uncertainty lineage. Workspace and docs re-observe because a failed callback does not prove the source remained unchanged. Agent follows the Plan-declared milestone and policy. Lifecycle refuses unsafe retirement until Execution supplies an attributable unresolved-operation or safe-point account.

### Cross-Agent Execution Coherence

Two Agents may independently authorize complete Tasks for the same Merkle scan over the same workspace revision. Execution Goal Set preserves two admissions. Execution Planning compares the full compatibility boundary and, when compatible, lowers one shared action node into the unified Task Network with attribution to both admissions.

One operational result yields one discharge record per admission. Each Agent then absorbs its own declared milestone and independently progresses its Plan or Goal. Sharing never merges Goal, Task, Plan, Agent, authority, or semantic satisfaction identities. Incompatible revisions, inputs, effects, authority, validity windows, or result schemas require distinct nodes.

### Successor Plan Reconciliation

When an admitted owner revision, Belief, causal mechanism, Regime position, directive, Capability catalog, authority, or projection policy changes, Agent requests a new complete `PlannerCut`. A refusal or changed cut invalidates stale product eligibility before new authorization.

Strategy reconstructs from the successor cut, predecessor Plan, and completed causal history. Agent records a new Plan judgment and preserves every historical authorization, owner result, and milestone under its original lineage. Neither Event arrival nor cut difference automatically authorizes work, and Execution never participates in reconstruction.

## Startup Nonce Product Proof

The approved `meld_startup` product is the first bounded runtime proof of the complete reconciliation path. It is one ordinary one-Agent PDS product, not a lifecycle coordinator or health authority. Its maintained condition is satisfied only when the current Startup Agent has durably incepted the deterministic nonce Goal and later accepted exact realization evidence for the matching Event under the same admission epoch.

```text
current generation and open admission epoch
-> deterministic Startup nonce instance
-> standing Curation expectation and bounded non-realization
-> Agent Goal inception
-> complete PlannerCut and Strategy Plan
-> independent Agent Task authorization
-> Execution admission and unified Task Network
-> global nonce.emit.v1 Capability
-> deterministic Event kind nonce
-> Graph visibility
-> independent Agent confirmation-operation authorization
-> terminal Curation result and configured Belief
-> Agent milestone acceptance
-> separate Goal satisfaction
```

The global `nonce.emit.v1` Capability and Event kind `nonce` remain reusable. They carry issuer, subject, ordered bounded correlation references, one fence reference, and contract revision. Startup meaning enters through the Task-selected references and installed Startup theory. The nonce owner fixes the Event grammar and rejects arbitrary Event fabrication without learning Agent, Goal, product, lifecycle, or runtime-health semantics.

The Event identity is known before append and the Goal identity is known before inception. Equal retries converge on the same Event and owner decisions. A successor admission epoch derives a successor nonce, so evidence from an earlier epoch cannot satisfy current Startup reconciliation.

Event durability and Execution outcome are independent positions. The Agent may validly satisfy the Goal after the exact Event returns while Execution still reconciles an uncertain provider callback. Inspection reports both positions and identifies the first missing success-critical consumer without collapsing operational readiness, nonce satisfaction, global health, or quiescence into one status.

This core proof is deliberately non-gating. It must run after structural readiness and epoch publication because those participants are required to complete it. Making other PDS activations depend on Startup satisfaction would add a live PDS-to-lifecycle relationship and is outside this candidate.

The complete product contract and exact edge projection are defined by the [Startup PDS full design](../startup_pds_design_requirements/startup_pds_design_specification.md) and [Startup semantic transition ledger](../startup_pds_design_requirements/semantic_transition_ledger.md). Outcomes `WMR-O29` through `WMR-O34` make the proof observable without changing `WMR-DD-01` through `WMR-DD-06`.

## Dependency Security Dissimilarity

The same structural spine carries different owner meanings:

```text
manifest and lockfile observation
-> exact inventory
-> advisory relation
-> applicability assessment
-> Goal and Plan when action is justified
-> mitigation Task outcome
-> successor inventory observation
-> successor assessment
-> explicit verification
```

Inventory, advisory, assessment, mitigation, successor observation, and verification are not interchangeable. The inspection projection labels and resolves each native identity rather than flattening them into a generic result chain.

## Lifecycle Product Proof

The integrated product remains correct when a consumer runs before its producer, a process restarts between commit and consume, a wake is broken, a participant incarnation is replaced, an external effect is uncertain, a successor generation becomes current, an old result arrives late, or retirement resumes after interruption.

For each scenario, inspection resolves the exact rows in the accepted lifecycle trace matrix and the corresponding product outcome matrix. It presents both before-and-after durable positions and never derives success from actor order, process health, polling, or shutdown.

## Inspection Identity And Freshness

One inspection request names assignment, generation or generation range, Agent or topology position, subject, perspective, branch, and requested temporal boundary. Every resolved item carries owner identity, immutable product identity, durable position, generation, incarnation when applicable, provenance, and freshness or conflict status.

The projection is repeatable for a frozen set of owner positions. A later request may show successor evidence. Inspection does not silently merge positions across generations, branches, perspectives, or product revisions.

## Evidence States

- `available` means the native owner resolved the exact identity and durable position
- `incomplete` means a declared producer or consumer position has not closed
- `stale` means the evidence does not satisfy the requested fence or successor boundary
- `conflicted` means identities or expected predecessors disagree
- `unavailable` means the named owner or transport cannot resolve the requested position
- `unproved` means design defines the evidence but no runtime artifact was supplied

These states are evidence descriptions. They do not judge program quality or authorize remediation.

## Program Boundary

This final design vertical proves composability of the accepted contracts. Revision 3 adds the approved Startup product as the first implementation-order proof without authorizing implementation. A later implementation program must create and directly test runtime evidence; these design receipts cannot substitute.
