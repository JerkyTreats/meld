# Startup PDS Program Insertion Assessment

Date: 2026-08-23

Status: assessed amendment boundary, core insertion authorized on 2026-08-23

## Question

Which parts of the World Model Reconciliation approval candidate would need tactical reopening if the full Startup PDS design were inserted as authoritative delivery-program material?

## Primary Finding

The core non-gating Startup PDS does not change the accepted owner contracts in `WMR-DD-01` through `WMR-DD-06`. It is a new integrated product proof over those contracts and a first implementation-order constraint.

The complete design therefore disproves the need for a broad program unfreeze. The smallest truthful amendment is concentrated at product proof, outcome traceability, program sequencing, review evidence, and the exact candidate manifest.

The optional dependent-product activation gate is different. Selecting that policy changes the accepted PDS and lifecycle relationship and requires a materially wider unfreeze.

## Core Canary Amendment

For the non-gating canary, the smallest authoritative insertion would reopen these surfaces:

| Frozen surface | Why reopening is required | Semantic change |
| --- | --- | --- |
| delivery program ledger | name the Startup PDS as the first runtime implementation proof and preserve its authorization state | delivery sequencing only |
| integrated product outcome matrix | add exact nonce outcomes and evidence owners | proof coverage only |
| integrated product proof and inspection | add the complete nonce trace and bounded claim | proof specialization only |
| cross-gate expected outcomes report | map each nonce outcome to accepted owner evidence | evidence map only |
| handoff ledger | add a product-specific projection from `SPDS-H01` through `SPDS-H23` to existing `WMR-H` edges, only if the standalone ledger is not accepted as the mapping authority | no owner change |
| folder index | connect the new design package | navigation only |
| revision 2 Gate Definition or a new bounded gate | make the added proof reviewable and separately acceptable | gate scope only |
| approval manifest | freeze the exact amended candidate | reproducibility only |
| independent approval recommendation | review the final exact candidate | assurance only |

The accepted detailed-design contracts remain referenced and frozen. Their existing Docs Freshness and Dependency Security examples need not be edited merely to add a third proof. The standalone design and transition ledger demonstrate how the canary uses each boundary.

## New Detailed Design Slice Assessment

A new `WMR-DD-08` is not required for the core canary. The product introduces a small reusable nonce owner, but its contract composes entirely through accepted native seams. Treating it as a new architecture vertical would overstate its authority and invite a second startup framework.

The clean program posture is one integrated product-proof amendment plus an implementation activation condition:

```text
implement the reusable WMR owner contracts
-> implement the minimal Startup PDS product
-> pass the exact Startup nonce proof
-> begin feature PDS runtime proof
```

If implementation discovery later proves that the nonce owner needs a new cross-domain contract rather than the accepted owner-publication and Capability seams, that evidence would trigger a new bounded detailed-design slice. The current full design does not prove that need.

## Accepted Designs That Remain Frozen

| Detailed design | Startup use | Reason no edit is required |
| --- | --- | --- |
| `WMR-DD-01` | nonce publication and immutable cut | contract already admits opt-in owner publication |
| `WMR-DD-02` | standing expectation and planned confirmation | one Curation authority already supports both invocation contexts |
| `WMR-DD-03` | mixed Plan and Agent progression | exact Task plus Epistemic Operation is the accepted Plan grammar |
| `WMR-DD-04` | Goal-attributed Task through unified Task Network | Execution remains ignorant of product semantics |
| `WMR-DD-05` | one-Agent product compilation and preparation | finite topology and native owner routing already cover the product |
| `WMR-DD-06` | structural barrier followed by current epoch | accepted lifecycle already separates ready, current, work, wait, and quiescence |

The cognitive architecture also remains valid. Persistent Domain Stewardship already permits product declarations, owner-issued packages, one-Agent topology, activation requirements, and native reconciliation after genesis.

## Optional Fail-Closed Amendment

If the user authorizes dependent PDS activation to require nonce satisfaction, these additional surfaces must reopen:

| Surface | Required change |
| --- | --- |
| product compilation and Agent genesis design | define a product-level activation prerequisite that cites an external owner receipt without making preparation live |
| activation generation and lifecycle design | define structural validation of the prerequisite reference while keeping root semantically blind |
| PDS cognitive architecture | state that PDS product control may remain active for declarative dependency policy after preparation |
| product and lifecycle transition ledgers | add exact producer, consumer, request, wait, wake, fence, restart, upgrade, and rollback positions |
| handoff ledger | add the Agent satisfaction receipt to PDS product-control request relationship |
| integrated product proof | prove bootstrap non-circularity, failure visibility, and dependent activation withholding |
| program ledger and gates | authorize and review the expanded architectural claim |

This is not a documentation-only proof refinement. It changes one accepted boundary statement and creates a new live producer-consumer relationship. It should not be bundled silently with the core canary amendment.

## Expected Implementation Scope After Approval

The likely implementation delta for the core canary is narrow:

- one first-party Startup PDS package and product declaration
- one small reusable nonce semantic owner or an explicitly approved equivalent owner
- one global `nonce.emit.v1` Capability implementation using Event append authority
- owner-route and hydration registration for the nonce publication
- installed standing and planned Curation theory
- installed Belief mapping and Agent satisfaction contract
- installed Strategy construction theory
- product topology, assignment, activation, and participant declarations
- startup nonce inspection specialization
- integrated fixtures covering the required proof scenarios

These are likely writes, not current authorization. Generic Agent, Strategy, Curation, Execution, Events, Graph, Traversal, Belief, lifecycle, and inspection implementations may require defect fixes when the proof first exercises them. Such fixes belong to the owner contract already accepted and are not Startup PDS semantics.

## Refused Expansion

The insertion does not justify a generic health domain, central runtime coordinator, PDS-owned graph truth, Event semantic validation, Execution startup guards, a private Task Network, a new Event store, recurring process polling as proof, `meld-lang` enforcement, or legacy Workflow integration.

## Tactical Unfreeze Recommendation

When explicit authorization arrives, unfreeze only the core proof amendment set first. Preserve `WMR-DD-01` through `WMR-DD-06` and the cognitive architecture as immutable dependencies. Add the Startup proof, review its exact evidence map, refresh the manifest, run one independent review, correct only frozen findings, and freeze again.

Keep the fail-closed activation policy outside that amendment unless it receives its own explicit authorization. Its value may be high, but its contract impact is categorically larger than the canary itself.

## Authorization Disposition

The user approved the full design and authorized core inclusion on 2026-08-23. The program reopened only the named integrated proof surfaces and created proposed `WMR-DG-07` revision 3. The fail-closed dependent-product activation policy remains unselected. Source implementation remains unauthorized.
