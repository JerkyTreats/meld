# PDS Boundary Program

Date: 2026-08-18
Status: active — `PB00` complete, `PB01` awaiting approval
Scope: close the superseded PDS implementation program, establish a clean compatibility checkpoint, and deliver the canonical cognition boundary through bounded product slices

## Objective

Preserve the generic PDS routing, owner revision, assignment, activation, and lifecycle substrate already implemented while removing cognition ownership from PDS packages. Documentation freshness must prove the first canonical boundary end to end. Dependency security must then falsify hidden docs assumptions before compatibility callers are retired.

## Program Completion Point

The program is complete when:

- the predecessor `W00` through `W06` ledger is closed honestly as superseded at a compatibility checkpoint
- the checkpoint is clean, reproducible, and protected by deterministic characterization
- new PDS packages contain stable semantic meaning rather than exact capabilities, construction policy, search controls, projection requests, authority requests, or current conclusions
- documentation freshness constructs and authorizes Strategy from separately owned current inputs
- documentation freshness belief revision consumes proof-carrying lower ground
- dependency security exercises the same boundary without shared application branches
- canonical runtime assembly no longer consumes `StrategyTheoryPackage` or `ResolvedStewardshipTheory`
- historical exact receipts remain readable through bounded compatibility decoding
- full verification and one bounded integrated review close the active scope

## Direct Product Proof

Given one routed documentation-freshness semantic package, one assignment, and one activation-local capability catalog, Meld derives a current Goal, constructs a candidate from separately owned Strategy inputs, authorizes and realizes it, admits documentation proof, revises belief, and reaches the maintained condition without any PDS body supplying the exact active toolbox, evaluation policy, search bounds, projection request, requested authority, or final freshness conclusion.

The dependency-security proof repeats the ownership test with coverage, currency, applicability, and negative-proof semantics. It is a falsification consumer, not a production security product.

## Governing Boundaries

- PDS supplies stable domain vocabulary, proof meaning, maintained norms, settlement obligations, and abstract action and outcome meaning.
- Meld supplies current facts, evidence admission, beliefs, Goals, Strategy problems, candidates, authorizations, tasks, outcomes, and reassessment.
- capability and activation supply the exact current affordance snapshot.
- Agent supplies construction policy and candidate judgment.
- Strategy owns problem construction, search, verification, and candidate identity.
- execution owns authority revalidation, realization, operation state, and effects.
- root, init, API, CLI, and serve remain adapters.
- compatibility readers may preserve historical bytes but may gain no new canonical callers.

## PB01 Documentation-Freshness Strategy Boundary Vertical

Goal: prove the canonical Strategy input split through the current deterministic docs product path.

Required behavior:

- install only stable Strategy semantic meaning through the PDS owner route
- assemble `StrategyProblem` from semantic theory, activation-local capabilities, current projection, Agent-owned policy, and explicit authority context
- place bounds only on `StrategySearchRequest`
- derive authority requirements from selected candidate actions
- preserve existing candidate, authorization, realization, and settlement behavior
- keep `StrategyTheoryPackage` as a historical compatibility antecedent only

Rejection gates:

- no renamed monolithic aggregate
- no package-carried exact capability list
- no package-carried evaluation policy, bounds, projection dimensions, or requested authority
- no new crate, store, background service, generalized registry, or compatibility caller
- no docs application branch in root, router, Meld Lang, or execution planning

Direct proof:

- the deterministic docs path reaches the same authorized five-step behavior from an activation-local capability snapshot
- removing one activation capability changes candidate construction without changing the semantic package identity
- changing search bounds changes only request identity and search completion
- changing authority context changes admission without changing semantic theory identity

## PB02 Documentation-Freshness Proof Boundary Vertical

Goal: move freshness judgment across the evidence boundary without letting docs publish a final belief conclusion.

Required behavior:

- docs publishes subject, source revisions, policy revision, coverage, contradiction, currency, completeness, calculation, and producer lineage
- belief owns the inference that updates the maintained proposition
- task completion, transport success, and publication success remain insufficient for restoration
- existing docs claim-validation meaning remains owner-controlled

Direct proof:

- identical task success with insufficient or contradicted proof does not restore freshness
- identical semantic package plus different admitted proof can produce different beliefs
- reopen preserves the proof and belief lineage needed to explain the result

No universal proof DSL or new evidence store is authorized.

## PB03 Dependency-Security Falsification Vertical

Required behavior:

- security PDS contains stable policy and proof meaning only
- exact scanners and read capabilities come from activation
- current inventory, advisories, coverage, and posture remain domain products

## Verification Strategy

Every active source-changing slice runs gates in this order:

1. direct product proof
2. `cargo fmt --all -- --check`
3. focused owner unit tests
4. focused cross-domain integration tests
5. reopen and historical-resolution tests
6. static ownership searches
7. `cargo test --workspace`
8. one integrated review
9. one bounded verification of accepted findings

Live provider evidence is required only when the slice changes provider-mediated behavior that deterministic fixtures cannot establish. Its output root must survive failure.

rg -n "StrategyTheoryPackage|ResolvedStewardshipTheory" src crates tests

Historical compatibility definitions and fixtures must be classified explicitly. A raw match is not automatically a failure, but every canonical caller is.

## Review Ownership

The program owns one integrated review per active product slice. Embedded implementation work does not create nested reviews. Findings freeze after the initial pass. Verification may examine only accepted findings and regressions caused by their correction.

If a fresh reviewer cannot be used, the result is a self-check and the next slice remains awaiting approval.

## Commit Model

Each completed product slice should land as one reversible commit by default. `PB00` may checkpoint predecessor code and aligned closeout documentation together because its purpose is to establish one exact baseline. Every commit requires the repository commit policy and a plain-language Commit Effect beginning with `If applied, this commit`.

No commit is authorized merely by this proposed program.
